# TOC Factory Game

Personal project. The design spec and source of truth is `docs/TOC-Factory-Game-Scope.md`.

## Development

- `npm run dev`, `npm test`, `npm run lint`, `npm run build` (type-checks, then builds to `dist/`).
- `src/engine/` is the framework-free, deterministic simulator; keep it free of React and of `Math.random`.
- Level content lives in `src/levels/`. `levels.test.ts` checks every level still teaches its lesson across many seeds, so run the tests after tuning any level.
- With `saturate` release, keep the first station slower than every non-constraint station, or piles form in front of the wrong stations (see spec §4.7).
- Free play's line builder (`src/sandbox/`) turns a few settings per station into an engine model; its default line is tested like a level.
- Class mode (`src/classroom/`, spec §8.4) runs on Firebase, and Firebase's code loads only when a device hosts or joins a class. Outside a class nothing a learner enters leaves the device, and a class receives only what its screen shows. `npm run test:class` tests it against Firebase's emulators (needs firebase-tools and Java). The database rules are `firebase/database.rules.json`; when they change, the owner must paste them into the Firebase console.
- The course guides (spec §8.5) are data in `src/course/`, shown by `src/ui/CourseGuide.tsx` and `TrainerGuide.tsx`. The trainer's script is one session per tier in `src/course/sessions/`; write its numbers as `{placeholders}` (filled from the engine in `facts.ts`), never typed in, and keep its wording of the class screen and level numbers (0.1, 3.2) the same as the game's. `course.test.ts` checks that every level is played once in order, every placeholder fills, and each plan's stated answer still earns every star, so run the tests after tuning a level, and update that level's segment when its wording or answer changes. The loading lab has its own place in the guides, outside the tiers: Session 11 for the trainer (`src/course/sessions/lab.ts`, talks only, since the lab has no levels and is not on the class screen), and for learners a card on the course map, key terms, a get-started section, and a notes prompt (`src/course/lab.ts`, `labInfo.ts`). Write its numbers as `{lab90}`, `{fleetOne}`, and so on, never typed in: `src/loading/facts.ts` works them out from the lab's model, and `course.test.ts` checks them, so run the tests after retuning the lab and reword the session if an answer changes.
- The exam and certificate (spec §8.6) are in `src/exam/`, shown by `src/ui/Exam.tsx` and its neighbors: a framework-free model (the pass mark and the extra questions in `rules.ts`, the draw, what is kept on the device, the certificate's text and ID, a small PDF writer) and the 100-question bank in `src/exam/bank/`. Question ids (`3-7`) are never renumbered or reused, because players' records refer to them. Each tier's count and quota are fixed by tests. A question must be answerable without the game or the course, must not give its answer away by length or wording (the tests measure it), and goes in `bank/sameIdea.ts` when it restates what another question's explanation says. Retuning a level or a principle means checking the questions that name it. The exam asks nothing of a learner's progress and sends nothing anywhere, a class included. The guides quote its numbers as `{examQuestions}`, `{examPass}`, and so on, never typed in.
- The loading lab (`src/loading/`, shown by `src/ui/LoadingLab.tsx` and `LabParts.tsx`) is a five-round game on load, cycle time, and how many bottlenecks a line has, ending with a round on lots and tool groups and one on hot lots promised sooner: a framework-free model (lines, the load-curve sweep, queue series, rounds and their missions in `loading.test.ts`; the lot-level simulator `lots.ts`, in which a lot is a customer's order for good wafers (its size is demand, not a lever) that must ship full and only when its last sublot is done, so orders are started for a chosen yield and a short one needs a top-up, and the workgroup is run with the whole fleet on one order (the norm, so orders never mix) or divided into single tools (on the workgroups that can be: `workgroups.ts` lists the four the lab offers, of 8, 6, 4, and 2 tools, and missions and promise times scale with each one's capacity), and each sublot runs out on its tools without mixing, with `lotRound.ts` and `lots.test.ts`; the lot round's screen is `LotLab.tsx`). Each round plays one fixed day so only the load changes; `loading.test.ts` checks across many days that each mission is winnable only by loading well. Retune a line, the spreads, or a mission, and rerun it. It is not part of the tiers, stars, class mode, or exam.
- My factory (`src/factory/`, shown by `src/ui/MyFactory.tsx` and `FactoryParts.tsx`) lets the owner type in a line of workgroups (tools, units per hour per tool, units per run, divisible or not), the demand, the order-size range, yield, variation, and the cycle time wanted, and shows the bottleneck, the cycle time, the demand that still meets the target, and what one more tool would do, all updating as numbers are typed. Demand is kept per day; the screen can count it per week (`perWeek`, `weekDays`), which only changes how it is shown and typed. A table of too low, midpoint, and too high cases (demand and batch size, `cases.ts`) can be saved as a CSV or a PowerPoint file (`deck.ts`, which loads `pptxgenjs` only on request); both are made on the device. Its step list renders from the live factory but reads results from a deferred copy, so every use of a step's results must allow for it not being there yet. Framework-free model in `model.ts`, `sim.ts` (a seeded flow-shop run over many orders), `words.ts`; `factory.test.ts` checks it. The `EXAMPLE` line is made up. Real factory numbers are typed in by the owner and stay in browser storage only (`loadFactory`/`saveFactory`); never put them in code, tests, docs, or commits. It is not part of the tiers, stars, class mode, the exam, or the guides.
- `docs/promo/` holds the promotional GIF and the scripts that rebuild it from the real game (see its README). Rebuild it when the game's look, level 1.1, or the name changes. `docs/promo/video/` builds the loading lab's 80-second explainer video, which the game serves from `public/loading-lab-explainer.mp4`; its spoken numbers are typed in `script.json`, so recheck them when round 1's line or the lab's spreads change (see its README).
- Style follows the Vite template: no semicolons, single quotes, explicit `.ts`/`.tsx` import extensions.
- Deployment: `.github/workflows/deploy.yml` lints, tests, and builds every push, and publishes the default branch to GitHub Pages once Pages is turned on for the repository (until then each run ends with a "Not published" warning). The build reads the Firebase web settings from the repository variable `FIREBASE_CONFIG`; without it the game builds without class mode.

## Independence log (every session)

This project must stay provably personal: the owner's own time, equipment, and accounts. See `independence/README.md`.

- First action of every session, before any other work: `node scripts/log-session.mjs start`, then commit `independence/` and push.
- When the user says they're done or wraps up: commit all work, then `node scripts/log-session.mjs end "<what was done, and the decisions the user made>"`, then commit `independence/` and push.
- At the first session after each project week ends (weeks start on `projectStart` in `independence/config.json`): also log `week "<summary>"`.
- If the script prints a FLAG (entry inside employer hours), ask the user why and record it with `note`.
- Never edit or delete anything under `independence/entries/`; corrections are new `note` entries.
- The repository is public: never write the owner's email, legal name, device serial numbers, or employer name into it.
- Never bring employer materials, data, or systems into this project.
